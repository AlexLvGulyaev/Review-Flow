## 🎯 1. Назначение продукта

### 🎯 1.1. Цель

Review Flow — демонстрационный MVP AI-системы обработки клиентских обращений, в которой бизнес-решения управляются явно, а не делегируются «чёрному ящику» языковой модели.

Система помогает команде поддержки:

- принимать обращения клиентов через публичный веб-интерфейс;
- классифицировать обращения и подбирать типовые ситуации из управляемой базы знаний;
- формировать черновики ответов в рамках утверждённой политики;
- контролировать качество ответов через оператора (Human-in-the-Loop);
- обучать базу знаний на реальных кейсах через механизм кандидатов;
- получать отчёты по обращениям, темам и качеству обработки.

### ⚠️ 1.2. Решаемая проблема

| Проблема | Последствие |
|----------|-------------|
| Полностью ручная обработка | Плохо масштабируется; растут издержки; качество зависит от отдельных сотрудников |
| Полностью автоматический LLM | Решения плохо контролируются, воспроизводятся и аудируются |
| «Модель решает за бизнес» | Организация не может формально делегировать принятие решений black-box модели |
| Отсутствие единой базы знаний ответов | Каждый оператор отвечает по-своему; несогласованный клиентский опыт |
| Новые повторяющиеся кейсы не становятся знаниями | Команда раз за разом решает одни и те же проблемы вручную |

### 💡 1.3. Решение

Review Flow использует архитектуру **Controlled Hybrid**:

- **Типовая ситуация (Response Case)** — Source of Truth бизнес-решения: политика ответа, утверждённая основа текста, атрибуты случая.
- **Retrieval** подбирает наиболее подходящую типовую ситуацию по примерам обращений.
- **Confidence** рассчитывается системой на основе результатов retrieval.
- **LLM не выбирает типовую ситуацию и не принимает бизнес-решение** — только адаптирует текст ответа в рамках `response_policy` / `approved_response_text`.
- **Оператор** остаётся Human-in-the-Loop: подтверждает, меняет или эскалирует.
- **Администратор** развивает базу знаний: типовые ситуации, retrieval-примеры, кандидаты.

Каждое обращение проходит прозрачный lifecycle: создание клиентом → обработка в backend → проверка оператором → публикация ответа. При необходимости оператор инициирует кандидата, который администратор превращает в новую или дополненную типовую ситуацию — замыкая learning loop.

## 🎬 3. Пользовательские сценарии

### 📝 Сценарий 1: Клиент создаёт обращение

**Кто:** Клиент  
**Цель:** Оставить отзыв, жалобу, предложение или вопрос и получить номер для отслеживания

**Шаги:**

1. Клиент открывает публичный Web UI Review Flow.
2. Нажимает **«Оставить отзыв»** и заполняет форму:
   - номер заказа/сделки;
   - тему (продуктовая область);
   - текст обращения;
   - email для проверки статуса;
   - имя и оценку (опционально).
3. Backend принимает обращение, сохраняет его в PostgreSQL, запускает Controlled Hybrid pipeline.
4. Система возвращает клиенту отображаемый номер обращения (`NL-...`).
5. Клиент сохраняет номер и email.

**Источники данных:** Web UI → Backend → PostgreSQL.

**Компоненты:** React Frontend → FastAPI Backend → PostgreSQL.

### 🔍 Сценарий 2: Клиент проверяет статус и читает ответ

**Кто:** Клиент  
**Цель:** Узнать, в какой стадии обращение, и прочитать опубликованный ответ

**Шаги:**

1. Клиент открывает страницу проверки статуса.
2. Вводит номер обращения и email.
3. Backend проверяет владельца обращения и возвращает клиентский статус.
4. Клиент видит понятные этапы: «обрабатываем», «на проверке», «опубликован ответ».
5. После публикации оператором клиент видит финальный текст ответа.

**Источники данных:** PostgreSQL (`reviews`, `review_responses`).

**Компоненты:** Web UI → Backend → PostgreSQL → Web UI.

**Важно:** клиент не видит внутренние термины (типовая ситуация, confidence, кандидаты).

### 👷 Сценарий 3: Оператор обрабатывает обычное обращение

**Кто:** Оператор  
**Цель:** Проверить предложенное решение, отредактировать ответ и опубликовать его

**Шаги:**

1. Оператор входит в контур компании (`/company`) под демо-учётной записью.
2. Открывает очередь обращений (`/operator/reviews`).
3. Выбирает обращение из списка — справа загружается карточка.
4. Видит:
   - текст обращения клиента;
   - предложенную типовую ситуацию (Response Case);
   - уровень confidence (Высокая / Средняя / Низкая);
   - альтернативные типовые ситуации (Top-N), если уверенность не высокая;
   - черновик ответа, собранный из policy и утверждённого текста ТС с адаптацией LLM.
5. При несогласии с предложением выбирает подходящую альтернативу.
6. Подтверждает типовую ситуацию (если требуется).
7. Редактирует текст ответа в поле «Ответ оператора».
8. Нажимает **«Одобрить и отправить»** — ответ публикуется.

**Источники данных:** PostgreSQL, управляемая база знаний Response Cases.

**Компоненты:** Operator UI → Backend → Controlled Hybrid Services → PostgreSQL.

### ⚠️ Сценарий 4: Оператор эскалирует обращение в базу знаний

**Кто:** Оператор  
**Цель:** Сигнализировать, что в KB нет подходящей типовой ситуации, и запустить learning loop

**Шаги:**

1. Оператор открывает обращение, для которого retrieval и альтернативы не покрывают кейс.
2. Нажимает **«Эскалация ТС»**.
3. Выбирает вариант **«Ни одна типовая ситуация не подходит»**.
4. Указывает сценарий, тональность, приоритет.
5. Описывает ситуацию в комментарии (обязательно).
6. Подтверждает эскалацию.
7. Backend создаёт кандидата для администратора.
8. Оператор может вручную отредактировать ответ и опубликовать его клиенту, не оставляя клиента без ответа.

**Источники данных:** PostgreSQL (`response_case_candidates`).

**Компоненты:** Operator UI → Backend → Candidate Service → PostgreSQL.

### 🛠️ Сценарий 5: Администратор управляет типовыми ситуациями

**Кто:** Администратор  
**Цель:** Вести базу знаний Controlled Hybrid

**Шаги:**

1. Администратор входит в контур компании и открывает `/admin/response-cases`.
2. Видит список типовых ситуаций с фильтрами.
3. Открывает карточку ТС и изучает поля:
   - код, название, продукт, тема;
   - сценарий, тональность, приоритет;
   - `response_policy` — правила ответа;
   - `approved_response_text` — утверждённая основа текста;
   - порог уверенности;
   - retrieval-примеры.
4. Создаёт новую ТС, редактирует существующую, добавляет примеры, архивирует или активирует.

**Источники данных:** PostgreSQL (`response_cases`, `response_case_examples`, справочники).

**Компоненты:** Admin UI → Backend → Response Case Service → PostgreSQL.

### 🔄 Сценарий 6: Администратор обрабатывает кандидата

**Кто:** Администратор  
**Цель:** Превратить операционный сигнал оператора в новое знание

**Шаги:**

1. Администратор открывает `/admin/response-cases` → вкладка **«Кандидаты»**.
2. Видит нового кандидата с контекстом обращения и комментарием оператора.
3. Принимает одно из решений:
   - **Создать новую типовую ситуацию** — заполняет форму, сохраняет.
   - **Объединить с существующей** — выбирает целевую ТС; текст обращения становится retrieval-примером.
   - **Отклонить** — указывает комментарий, в базу знаний изменений не вносит.
4. После одобрения кандидат становится retrieval-примером.
5. Последующие похожие обращения распознаются с более высокой уверенностью.

**Источники данных:** PostgreSQL (`response_case_candidates`, `response_cases`, `response_case_examples`).

**Компоненты:** Admin UI → Backend → Candidate Admin / Response Case Services → PostgreSQL.

### 📊 Сценарий 7: Руководитель смотрит отчёты

**Кто:** Руководитель / аналитик  
**Цель:** Понять нагрузку, тематику и качество обработки обращений

**Шаги:**

1. Пользователь открывает `/reports` после входа администратора.
2. Выбирает период: сегодня, 7/30/90 дней или произвольный диапазон.
3. Просматривает отчёты:
   - **Обращения клиентов** — объём, обработка, средний рейтинг, динамика, распределения.
   - **Бизнес-сводка** — топ жалоб, предложений, благодарностей, новые темы.
   - **Качество Controlled Hybrid** — coverage, override rate, low confidence rate, проблемные ТС.
4. При необходимости экспортирует отчёт в CSV, XLSX или PDF.

**Источники данных:** PostgreSQL (`reviews`, `response_case_decisions`, `case_match_results`, `operational_logs`).

**Компоненты:** Reports UI → Backend → Reports Service → PostgreSQL.

### 🤖 Сценарий 8: Администратор настраивает промпты и AI-провайдеров

**Кто:** Администратор  
**Цель:** Управлять поведением LLM-адаптации и выбором провайдера

**Шаги:**

1. Администратор открывает `/settings/system` или `/settings/ai-providers`.
2. Видит список AI-провайдеров (mock, OpenAI-compatible, GigaChat, ProxyAPI) и текущие эффективные настройки.
3. Выбирает активного провайдера и fallback.
4. Редактирует системный промпт адаптации ответа (`review_response_generation`) — сохранение создаёт новую версию.
5. Настраивает runtime-параметры Controlled Hybrid:
   - Top-K кандидатов retrieval;
   - minimum match score;
   - confidence thresholds;
   - draft on medium / auto decision on high.

**Источники данных:** PostgreSQL (`ai_provider_settings`, `prompt_versions`, `ch_runtime_settings`).

**Компоненты:** Admin UI → Backend → Settings Services → PostgreSQL.

### 📈 Сценарий 9: Администратор оценивает качество ответов

**Кто:** Администратор  
**Цель:** Контролировать качество AI-черновиков и корректировать промпты

**Шаги:**

1. Администратор открывает `/evaluation`.
2. Добавляет обращение в набор для ручной оценки.
3. Просматривает обращение, его черновик, финальный ответ, версию промпта.
4. Проставляет операторскую оценку (1–5) и комментарий.
5. Использует результаты для принятия решения о смене активной версии промпта.

**Источники данных:** PostgreSQL (`evaluation_cases`, `reviews`, `review_responses`, `prompt_versions`).

**Компоненты:** Evaluation UI → Backend → Evaluation Service → PostgreSQL.

## 🛡️ 5. Бизнес-правила и ограничения

| ID | Правило | Обоснование |
|----|---------|-------------|
| BR-1 | **Response Case является Source of Truth бизнес-решения** | Бизнес-решение фиксируется в управляемом артефакте KB, а не в свободной генерации |
| BR-2 | **LLM не выбирает типовую ситуацию и не принимает бизнес-решение** | Контроль качества, аудит и воспроизводимость |
| BR-3 | **Retrieval подбирает ТС по примерам; confidence вычисляется системой** | Прозрачность оснований для выбора |
| BR-4 | **Оператор — финальная инстанция публикации ответа** | Ответственность за коммуникацию с клиентом остаётся у человека |
| BR-5 | **Клиент не видит внутренние статусы, confidence и типовые ситуации** | Защита операционной модели и упрощение UX |
| BR-6 | **Каждый кандидат обрабатывается администратором: новая ТС, объединение или отклонение** | KB развивается под контролем эксперта |
| BR-7 | **Промпты и настройки AI-провайдеров версионируются** | Возможность отката и сравнения качества |
| BR-8 | **API-ключи и токены не возвращаются в ответах и не коммитятся в репозиторий** | Безопасность |
| BR-9 | **Staff-вход по Bearer-токену, публичный demo-вход — только просмотр (read-only RBAC); это не корпоративный SSO** | Честное описание ограничений MVP |

|----|------------|
| NFR-6 | API-ключи AI-провайдеров хранятся только в переменных окружения; `.env` не коммитится |
| NFR-7 | Публичный Web UI не имеет прямого доступа к БД |
| NFR-8 | Все внешние endpoints (demo) работают по HTTPS |
| NFR-9 | Административные endpoints требуют заголовка `X-Role: administrator` |
| NFR-10 | Публикация не содержит клиентских данных и внутренних APL-артефактов |

### 🏗️ 6.3. Сопровождаемость и масштабируемость

| ID | Требование |
|----|------------|
| NFR-11 | База знаний (Response Cases + примеры) может быть полностью пересоздана из SQL-миграций |
| NFR-12 | Конфигурация промптов и настроек версионируется |
| NFR-13 | История административных действий и operational events сохраняется в логах |
| NFR-14 | Проект развёртывается одной командой `docker compose up --build` |

## ✅ 7. Критерии приёмки

### ✅ 7.1. Общие критерии

| Критерий | Признак |
|----------|---------|
| Клиент может создать обращение | Web UI отображает номер обращения без ошибок |
| Клиент может проверить статус | Web UI отображает понятный этап обработки |
| Оператор видит обращение в очереди | `/operator/reviews` содержит созданное обращение |
| Оператор может опубликовать ответ | После approve клиент видит `final_response` в статусе |
| LLM не публикует ответ самостоятельно | Публикация требует действия оператора |

### 🧭 7.2. Controlled Hybrid

| Критерий | Признак |
|----------|---------|
| Retrieval предлагает типовую ситуацию | В карточке оператора видна «Выбранная типовая ситуация» |
| Confidence отображается корректно | Метка «Высокая / Средняя / Низкая» соответствует score |
| Альтернативы показываются при низкой уверенности | Виден список «Альтернативные типовые ситуации» |
| Оператор может создать кандидата | После эскалации в `/admin/response-cases` → «Кандидаты» появляется новая запись |

### 🛠️ 7.3. База знаний

| Критерий | Признак |
|----------|---------|
| Администратор создаёт ТС | Новая запись появляется в списке типовых ситуаций |
| Присоединение кандидата добавляет пример | У целевой ТС увеличивается количество retrieval-примеров |
| Архивация работает | Архивированная ТС не участвует в подборе |

### 📊 7.4. Отчётность

| Критерий | Признак |
|----------|---------|
| Отчёты загружаются | `/reports` отображает данные без ошибок API |
| Экспорт работает | Файл CSV/XLSX/PDF скачивается |
| Логи доступны | `/logs` отображает события pipeline |

## 📦 8. Границы первой производственной версии

### ✅ Входит в первую версию (MVP)

- Docker Compose: PostgreSQL 16, FastAPI backend, React frontend.
- Клиентский контур: создание обращения, проверка статуса, просмотр опубликованного ответа.
- Controlled Hybrid pipeline: retrieval → confidence → draft generation → операторская проверка.
- Операторская консоль: очередь, карточка обращения, confirm/override/candidate, публикация.
- База знаний Response Cases: CRUD ТС, управление примерами, обработка кандидатов.
- Legacy pipeline (по флагу `CH_PIPELINE_ENABLED=false`) для регрессии.
- Ролевая модель: ops RBAC по Bearer-токену (`OPS_*_TOKEN`, роли administrator/operator/demo), публичный demo-вход — read-only; legacy `X-Role` — только dev-fallback.
- Промпты, evaluation, operational logs.
- Отчёты: обращения клиентов, бизнес-сводка, качество Controlled Hybrid.
- Настройки AI-провайдеров и runtime-параметров CH.
- Документация и материалы для портфолио.

### ❌ Не входит в первую версию

- Production аутентификация (SSO, OAuth2, API-токены).
- Полностью автоматическая публикация без оператора (auto-publish по policy).
- Версионирование Response Cases.
- Интеграция с внешней CRM / тикет-системой / маркетплейсом.
- Многоязычный интерфейс (первый язык — русский).
- Мобильное приложение.
- Kubernetes / Terraform / CI/CD.
- Multi-tenant режим.
- Полный документный RAG вместо Controlled Hybrid.
